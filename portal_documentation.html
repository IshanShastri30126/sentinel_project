01. Executive System Overview

The Chakravyuh Club Portal 2.0 is an enterprise cybersecurity interest group management ecosystem designed for the Computer Engineering Department at CSPIT, CHARUSAT University. The portal unifies event registration, attendance tracking via QR scanner consoles, dynamic certificate verification, role-based clearance permissions, and team roster management.

Core Technology Stack
  • Frontend Framework: Next.js 16 (React 19, Turbopack, Framer Motion 3D, Lucide Icons, Vanilla Tailwind/CSS).
  • Backend Engine: Node.js + Express.js TypeScript micro-server architecture.
  • Database Tier: PostgreSQL managed via Prisma ORM v5 with strictly typed prepared statements.
  • In-Memory Cache & Rate Limiting: Redis v7 instance for session state, API request throttling, and fast leaderboard reads.
  • Storage & Delivery: Cloudinary API for encrypted document and image asset delivery.

03. Backend Architecture & REST API

The backend micro-service operates on Node.js + Express.js (TypeScript) located under the server/ directory. All incoming HTTP requests pass through a defensive middleware security pipeline before reaching modular router endpoints.

Primary Micro-Server REST Endpoints

Method & Endpoint Auth / Role Functionality
POST /api/auth/register Public Registers user, hashes password (bcrypt), sanitizes 10-digit phone, returns complete user payload.
POST /api/auth/login Public Authenticates credentials, issues JWT token and HttpOnly session cookie, updates audit log.
GET /api/users/me Authenticated Retrieves active authenticated user dossier including studentId / employeeId, role, and department.
PATCH /api/users/profile Authenticated Updates profile attributes (phone sanitized to 10 digits; faculty replaces studentId with employeeId).
POST /api/events Coordinator / Core Creates new event; automatically includes Faculty Coordinators and organises team roster.
POST /api/events/:id/register Authenticated Registers student for an event, checks capacity, generates dynamic QR code registration pass.
GET /api/settings/landing-team Public Fetches officer team roster sorted by hierarchy clearance (Faculty -> Coordinator -> Tech -> Media).
POST /api/approvals/:id/decide Core / Admin Decides pending event clearance request (APPROVED / REJECTED) with audit logging.

Middleware Pipeline Pipeline Execution Sequence

  1. Helmet Headers: Suppresses X-Powered-By, enforces CSP, HSTS, and X-Frame-Options: DENY.
  2. Rate Limiter (Redis): Throttles IP requests to 100 req/15min to prevent brute-force attacks.
  3. CORS Policy: Strictly validates origin against CLIENT_URL allowlist.
  4. Cookie Parser: Parses encrypted HttpOnly cookies.
  5. Authentication Guard (authMiddleware): Verifies JWT signature and extracts identity.
  6. Role Access Guard (requireRole): Enforces role authorization (FACULTY, STUDENT_COORDINATOR, TECH, MEMBER).
  7. Audit Logger: Records timestamp, user ID, IP address, endpoint, and outcome into audit table.

05. System Operation & Workflows

The portal manages critical event lifecycles, user registrations, certificate generation, and member verification.

1. User Authentication & Profile Lifecycle

  1. User visits /auth and submits signup form specifying Role (STUDENT / FACULTY / COORDINATOR).
  2. Form enforces 10-digit numeric mobile validation (clearing non-numeric input).
  3. Server hashes password using bcrypt with salt round 12, creates database record, generates JWT, and sets HttpOnly cookie.
  4. Client receives full user payload (`studentId` or `employeeId`, `department`, `institute`, `semester`).
  5. Profile section on /dashboard/profile displays dossier. For Faculty roles, Student ID changes to Employee ID, and Semester is omitted.

2. Event Creation & Organizer Auto-Population Workflow

  1. Coordinator logs in and navigates to /dashboard/events -> clicks Create Event.
  2. Client automatically queries /api/settings/landing-team for active roster officers.
  3. System automatically pre-populates all Faculty Coordinators into the event organizers array.
  4. Form provides a Student Coordinator dropdown selector; choosing a coordinator auto-fills their Name, Role, Email, and Phone.
  5. Upon submission, if required, an EVENT_PERMISSION request is sent to Core Admin for approval.

06. Cookie Storage & OWASP Security

Security is implemented based on the OWASP Top-10 specifications.

Session Cookie Storage Mechanics

Authentication session tokens are delivered via HttpOnly, Secure, SameSite=Strict HTTP Response Cookies named chakravyuh_session.

  • HttpOnly Flag: Prevents client-side JavaScript (e.g. document.cookie) from reading the cookie, completely mitigating Session Hijacking via XSS.
  • Secure Flag: Ensures cookies are transmitted exclusively over encrypted HTTPS connections in production.
  • SameSite=Strict: Inhibits browser from sending session cookies on cross-site requests, mitigating Cross-Site Request Forgery (CSRF).

OWASP Security Controls Checklist

Security Domain Implementation Mechanism
Input Validation Server-side allowlisting, regex numerical extraction (`\D`), canonicalization, parameter truncation.
Output Encoding Context-aware HTML body, attribute, and JavaScript encoding to prevent Cross-Site Scripting (XSS).
SQL Injection Defense 100% prepared parameterized queries enforced via Prisma ORM engine. Zero raw concatenated SQL strings.
Password Hashing Bcrypt algorithm with salt factor 12. Generic error response ("Invalid credentials").
Access Control Deny by Default. Server-side role authorization checks (`requireRole`) on every API request.
Audit Logging All auth, access denial, and approval decisions written to AuditLog table with UTC timestamp and IP.

07. Redis Caching & Cloud Services

1. Redis In-Memory Engine Roles

Redis v7 acts as the high-speed caching and rate-limiting memory store.

  • API Rate Limiting: Tracks client IP request frequencies (key: ratelimit:ip:{ip}) with TTL window reset.
  • Session Cache: Caches active JWT invalidation blacklists for immediate session termination on logout.
  • Roster & Leaderboard Caching: Caches landing team roster queries (cache:landing_team) with 10-minute cache expiration, reducing PostgreSQL query overhead.

2. Cloudinary File Upload Integration

File uploads (event posters, document guides, avatar images) are managed securely:

  1. Multer middleware receives multipart file upload in memory.
  2. Validates file extension allowlist (.jpg, .png, .webp, .pdf) and MIME header.
  3. Generates non-predictable UUID filename.
  4. Streams file buffer directly to Cloudinary authenticated storage API.
  5. Stores returning HTTPS CDN URL in database.

10. Rate Limiting & TCP/SYN Flood Defense

The platform implements enterprise-grade multi-tier defenses against brute-force authentication attacks and network-layer Denial of Service (DoS / TCP / SYN flood) attacks.

1. Progressive Login Rate Limiting & Evasion Prevention

The authentication gateway (/api/auth/login) enforces progressive lockouts tracked simultaneously by Client IP Address and Target Account Email to prevent evasion via Incognito, Private Browsing, cookie clearing, or IP rotation:

  • Initial Allowance: 4 failed login attempts permitted per IP / email pair.
  • Tier 1 Lockout (20 Minutes): Reaching 4 failed attempts triggers an automatic 20-minute (1,200 seconds) complete access block. Requests from any browser window or device targeting the blocked IP or account are rejected with HTTP 429 and a live countdown timer.
  • Tier 1 Expiry (1 Chance): Upon 20-minute expiry, the user/IP receives exactly 1 attempt (5th attempt). If successful, attempt counters and lockouts are cleared to 0.
  • Tier 2 Lockout (5 Hours): If the 5th attempt fails, the user/IP is placed under a strict 5-hour (18,000 seconds) maximum security lockout.

2. TCP & SYN Flood Defense Architecture

Defenses operate across both application (Node.js runtime) and network infrastructure (Linux OS Kernel & Firewall) layers:

A. Node.js Runtime HTTP Server Hardening

// Node.js TCP Socket & HTTP Header Timeout Configuration (server/src/index.ts)
httpServer.headersTimeout = 10000;    // 10s header read limit (prevents Slowloris attack)
httpServer.requestTimeout = 15000;    // 15s max request duration
httpServer.keepAliveTimeout = 5000;   // 5s idle connection release
httpServer.maxHeadersCount = 100;     // Prevents header flood memory consumption

// Active TCP Socket Connection Limiter
const activeConnectionsByIp = new Map<string, number>();
httpServer.on("connection", (socket) => {
  const ip = socket.remoteAddress || "127.0.0.1";
  const count = (activeConnectionsByIp.get(ip) || 0) + 1;
  activeConnectionsByIp.set(ip, count);

  if (count > 50) {
    // Destroy sockets exceeding 50 concurrent TCP connections per IP
    socket.destroy();
  }
});

B. Linux OS Kernel SYN Flood Hardening (/etc/sysctl.conf)

# Enable SYN Cookies when TCP SYN backlog fills up
net.ipv4.tcp_syncookies = 1

# Increase max TCP SYN queue size
net.ipv4.tcp_max_syn_backlog = 4096

# Limit SYN-ACK retries before dropping half-open connection
net.ipv4.tcp_synack_retries = 2

# Fast socket release on FIN-WAIT-2
net.ipv4.tcp_fin_timeout = 15

C. Firewall & NGINX Reverse Proxy Rate Limiting

# iptables SYN flood mitigation rule
iptables -A INPUT -p tcp --syn -m limit --limit 1/s --limit-burst 3 -j ACCEPT

# NGINX Connection Limiting (/etc/nginx/nginx.conf)
limit_conn_zone $binary_remote_addr zone=conn_limit_per_ip:10m;
limit_conn conn_limit_per_ip 30;
